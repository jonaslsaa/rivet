# PORTING.md — Java → Rust pattern map

The canonical translation guide. Every implementer and reviewer prompt includes this file. When a bug class recurs, the fix lands *here* first (via a dedicated PR), then affected units are re-run.

## Module & naming conventions

- Java package → Rust module path in the crate the coverage ledger assigns (D15): `net.minecraft.world.entity.monster` → `rivet_server::world::entity::monster`. The ledger computes the crate and the path from the class graph; never choose either by hand.
- One Java class → one Rust module file of the same name in snake_case (`ServerPlayer.java` → `server_player.rs`), unless the class is trivial (<50 lines) and package-private — then fold into the parent module.
- **A class over 2,000 Java LOC becomes a directory module** (`living_entity/`). `mod.rs` holds the struct, constants, constructors and nested-type declarations in Java order; the members follow split across files in Java source order: inherent `impl` blocks for non-virtual receiver-form methods, free functions for handle-form methods and for the bodies of virtual methods (OWNERSHIP.md §Class hierarchies), each file one contiguous run of the Java source (about 500–1,000 Java lines), named after its first member (`living_entity/hurt_server.rs`) and opening with a comment giving its Java line range. Never reorder members across files. Such a class is its own manifest unit (ROADMAP §3.2).
- Keep Java names translated only by case convention (`getBlockState` → `block_state` for getters, `setBlockState` → `set_block_state`). Do not "improve" names — greppability against the Java source is a feature.
- Method overloading: suffix by discriminating arg (`teleport_to`, `teleport_to_with_rotation`). Constructors: `new`, then `new_with_*` / `from_*`.

## Types

| Java | Rust | Notes |
|---|---|---|
| `int`, `long` | `i32`, `i64` | **All arithmetic wrapping** unless proven range-safe: `wrapping_add/mul/...` or `Wrapping<T>`. Overflow panics in debug are ports bugs. |
| `>>`, `>>>` | `>>` on `iN` / on `uN` (cast) | Java `>>>` = logical shift: `((x as u32) >> n) as i32`. |
| `float`, `double` | `f32`, `f64` | Keep precision level exactly — do not widen f32 math to f64. `Math.floor(d)` then `(int)` cast: Java float→int casts **saturate**; Rust `as` also saturates (post-1.45) — OK, but keep NaN→0 semantics in mind. |
| `boolean`, `byte`, `short`, `char` | `bool`, `i8`, `i16`, see below | Java `byte` is signed. |
| `String`, `char` | `String`/`&str`, but | Java is UTF-16: `length()`/`charAt`/`substring` indices are UTF-16 code units. Where indices are observable (chat, NBT string limits, command parsing) count UTF-16 units, not bytes. |
| `T[]`, `List<T>` | `[T; N]`/`Vec<T>` | |
| `Optional<T>` / nullable | `Option<T>` | Every dropped Java null-check is a review finding. |
| `Map`/`Set` | `HashMap`/`HashSet` (hashbrown via std) | **Iteration order differs from Java.** If order is observable (serialization, ticking, packets), flag it: use `IndexMap`, a sort, or document why order can't matter. |
| `UUID` | `uuid::Uuid` | Java `UUID(mostSig, leastSig)` ordering. |

## Structure

- **Class hierarchy → struct embedding + the OWNERSHIP.md dispatch pattern.** Superclass fields become an embedded struct field named after the parent: `struct Zombie { monster: Monster, ... }` (chain continues downward). Virtual methods go on `<Class>Behavior` value traits (receiver form) or `<Class>Dispatch` traits (handle form); each Java body is a free function in its class's module; `super.foo()` → direct call to the parent class's free function; virtual calls on `this` always dispatch dynamically. Routing of inherited overrides, accessors and `as_*` methods is generated by the family scaffold, never hand-written. Storage and dispatch are defined in `OWNERSHIP.md` §Class hierarchies — do not choose per unit.
- **Java references to game objects → handles** (`EntityKey`, `BlockEntityKey`, `LevelId`, slot handles), resolved through `LevelCtx` at each use. Whether a method is handle form (`fn m(ctx: &mut LevelCtx, this: Key, …)`) or receiver form (`&self`/`&mut self`) follows OWNERSHIP.md §Receivers and handles; never hold a borrow of game state across a call that takes `ctx`, and never add a queue or take an object out of its arena to get past the borrow checker.
- Interfaces → traits. Abstract classes → embedded struct + trait with required methods.
- Inner/anonymous classes → nested structs or closures; static nested → sibling module.
- `static final` constants → `const`/`static`; static mutable state / static init blocks → `LazyLock` (and note it — static init order dependencies are a drift risk).
- `synchronized`/`volatile`: game-state code is tick-thread-confined (D5) — usually drop with a `// tick-thread` note; genuinely cross-thread state (network, chunk IO) → explicit `Mutex`/`RwLock`/atomics. Never silently drop.
- Checked exceptions → `Result<T, E>` with `thiserror` enums per crate. `IllegalStateException`-style unchecked → `panic!` only where vanilla crashing is the actual observable behavior; otherwise `Result`.
- `equals`/`hashCode` → `PartialEq`/`Hash` derives when value-semantic; identity-semantic Java classes (`==` on references) compare by arena ID, never derive blindly.
- Java streams / iterators → iterator chains; beware eager vs lazy: `unwrap_or(f())` evaluates eagerly — use `unwrap_or_else`.
- `instanceof X` → the generated `as_x()` accessor when X has subclasses or is an interface, an `Any` downcast when it has none (OWNERSHIP.md §Class hierarchies).

## Minecraft-specific

- **RNG parity is sacred.** `LegacyRandomSource` (java.util.Random LCG), `XoroshiroRandomSource`, and `Mth.sin`'s 65536-entry lookup table are ported bit-exactly in `rivet-util` with golden tests against Java-generated fixtures. Never substitute `rand` or `f32::sin` in gameplay/worldgen code.
- **`Mth` transcendentals (`COS_TAB`/`ASIN_TAB`) are native-platform parity (D14).** Paper 26.2 builds them at class-init time with `java.lang.Math.cos`/`Math.asin`. The resulting `COS_TAB` differs by up to 1 ULP between x86_64 and aarch64 — exactly 11 of its 257 entries — while `ASIN_TAB` is bit-identical.
  - Rivet carries **independently generated, compile-time selected per-architecture `COS_TAB` variants** and matches **native Paper per supported platform**, not a single cross-platform constant. `ASIN_TAB` is shared because it is bit-identical on both supported architectures. x86_64 Linux with Temurin 25 is the primary development/release-gate target; aarch64 stays supported and must have its own verified generated `COS_TAB`.
  - Canonicalize floating golden bits with `Float.floatToIntBits`/`Double.doubleToLongBits` semantics (canonical NaN, every non-NaN bit exact), matching the oracle.
  - **`Math.min`/`Math.max` return the first operand for same-sign zero pairs.** For mixed-sign zeroes, `max` returns `+0.0` and `min` returns `-0.0`; port with explicit sign bits, never Rust's `f32::min`, `f32::max`, `f64::min`, or `f64::max`.
  - **Never** substitute `StrictMath` and **never hand-edit** a generated table. Regenerate on each target via the fail-closed codegen path (host-architecture-only writes, provenance-checked aarch64 table, `compile_error!` on unsupported architectures).
- Hashing used in game logic (e.g. `String.hashCode`, position hashes) is ported exactly — Java's `hashCode` algorithms live in `rivet-util::java_hash`.
- Codec/DataFixerUpper: `rivet-serialization` ports the DFU Codec API shape (MIT). External formats (JSON datapacks, configs) may use `serde` underneath, but Codec semantics (error accumulation, partial results) are preserved.
- NBT: `rivet-nbt`, ported types + SNBT; golden round-trip tests against real region files.
- Text components: port Paper's Adventure usage (Adventure is MIT) as `rivet-text`.
- Registries/data-driven content: **generated, not hand-ported** — `rivet-registry` codegen from vanilla data extraction. If you're hand-typing block properties, stop.

## Canonical homes

- Every type has exactly one definition, at the mirrored path in the crate the ledger assigns (D15). **Defining any hub type of ROADMAP Appendix A outside its canonical home is forbidden**: no stand-in, private copy, "minimal local" mirror or parallel struct (today's duplicates of `Vec3`, `BlockPos`, `AABB`, entity ids and `ItemStack` are exactly this). Use the canonical type, or, when the hub is not ported yet, stop and report it so the controller moves it to the front of the spine queue (ROADMAP §3.7). The gate's single-definition check enforces this; its allow-list only shrinks.
- A missing *leaf* dependency gets a minimal declaration at the leaf's own mirrored path, marked `// STUB(<owning unit id>)`, never a local substitute.
- A class split across crates by D15 keeps one struct; the live-game half is an extension trait `<JavaClass>Live` or dispatch-pattern traits, never a second struct.

## Tests (D18)

- Tests that earn verification credit: ported Paper JUnit tests for a class with a direct Rust twin (translated with the class, never weakened), tests whose expected values come from a Java-generated fixture with provenance (or derive from one), and differential rows (oracle ops, world-state diffs, arena traces, client scenarios, GameTest runs on both servers).
- Hand-written tests are fine for ownership invariants, error paths and Rust-only seams, and earn no credit. Never hand-type a value or ordering that Paper computes, and never record Rivet's own output as a golden.
- A port PR never edits a fixture, golden (`*.jsonl`/`*.tsv`), exclusion table, comparator or normalizer; those change only in verification PRs, reproducibly by `regen`. A failing golden is a `blocked` finding, not something to adjust.
- Tests assert closure counts, so they cannot pass on an empty corpus, an all-dropping filter or a missing file.

## Forbidden

- `todo!()`/`unimplemented!()` without a `blocked` note in the manifest/issue.
- Inventing APIs not present in the Java source; "improving" logic during translation (file an issue instead).
- Inventing a trait seam where Java has a concrete class, for example to break a crate cycle (D15 places the classes instead).
- Defining a hub type outside its canonical home, or any stand-in for one (§Canonical homes).
- Take-tick-putback of an object `ctx` can resolve, or a deferred queue Java does not have (OWNERSHIP.md §Receivers and handles).
- Copying code from `working/Pumpkin` (D7).
- Weakening/deleting tests or fixtures to pass gates (D8).
- `git stash`, `git reset`, force-push, editing reference docs mid-wave.
- `unsafe` outside `rivet-ffi` without a justifying comment and reviewer sign-off.

## Review drift checklist

Reviewers hunt these specifically: wrapping arithmetic omissions · `>>>` mishandling · HashMap order observability · UTF-16 index drift · f32/f64 widening · `Mth` table vs libm calls · dropped null-checks · eager `unwrap_or` · identity-vs-value equality · dropped `synchronized` without note · side effects in `debug_assert!` · `as` casts changing overflow/NaN semantics · off-by-one from Java's inclusive/exclusive idioms · a borrow of game state held across a `ctx` call, or an invented queue or take-out to dodge one · hand-written override routing · a hub type defined outside its canonical home.

Test and verification checks (docs/VERIFICATION.md §6.3, D18), in every review:

1. For each new assertion with a literal expected value: where did the value come from? Accept only (a) a recorded golden with a manifest, (b) a value the test derives from such a golden, or (c) a Rust-only invariant with no Paper counterpart. Flag everything else as `fabricated-expectation`.
2. Did the diff touch a file under `fixtures/`, a `*.jsonl`/`*.tsv` golden, an exclusion table, or a comparator or normalizer? In a port PR that is a blocking finding.
3. Can the test pass vacuously (empty corpus, `if let Some` around the assertion, a filter that drops every row, an early return when a file is missing)? Require closure counts.
4. Does a test compare Rivet output to Rivet output (round trip only, snapshot of its own output)? It earns no verification credit: say so and list the file as uncovered.
5. Is any nondeterminism handled by widening the comparison (epsilon, sorting, dropping a field) instead of by seeding, or by a recorded exclusion justified by Paper twin runs?
6. In a verification PR: does the Java probe or op call Paper's real code path, or re-derive the answer itself? A probe that reimplements the logic is an oracle of itself.
