# OWNERSHIP.md — memory architecture

How Java's GC'd, cyclic object graph maps to owned Rust data. This is decided **here, per subsystem, never per unit**. Implementers follow it; reviewers audit against it. It changes only through dedicated PRs (D9); ROADMAP R5 is the signal that would reopen the entity model. Crate placement of every class is D15's ledger, not this file.

## The rule

**One owner, IDs everywhere else.** Game state has exactly one owner: `MinecraftServer` on the tick thread (D5). A Java reference to a game object (`entity.level`, `this.mob`, `damageSource.getEntity()`, `blockEntity.level`, `player.containerMenu`) becomes a **handle**, an ID or key resolved through the owner at each use. No Rust borrow of game state is held across a call that can reach game state. `Arc<RwLock<T>>` on game state is forbidden; the exceptions are listed at the end.

## Ownership tree

```
tick thread
├── MinecraftServer                                  all game state; one &mut at a time
│   ├── entity arena: SlotMap<EntityKey, Box<dyn EntityBehavior>>
│   ├── block-entity arena: SlotMap<BlockEntityKey, Box<dyn BlockEntityBehavior>>
│   ├── level arena: SlotMap<LevelId, ServerLevel>
│   │   └── ServerLevel { level: Level, … }
│   │       ├── chunk source / ChunkMap: LevelChunk by value
│   │       │     sections (palettes), heightmaps, light, POI,
│   │       │     block_entities: BlockPos → BlockEntityKey      (index only)
│   │       ├── EntityLookup (Moonrise): by-int-id, by-uuid, section, tick-list, tracking indices of EntityKey
│   │       ├── block-entity ticker list
│   │       └── scheduled ticks, block events, raids, saved data, LevelData, …
│   ├── levels: ResourceKey<Level> → LevelId           Java's LinkedHashMap, insertion order
│   ├── PlayerList: EntityKey ↔ ConnectionId ↔ UUID indices
│   ├── singleton_fields                              behaviour-singleton state (§Mutable singleton state)
│   └── server services: commands, recipes, advancements, scoreboard, …
└── PluginBridge                                     beside the server; no game state (§Events)
    └── JVM (in-process): plugin code runs here, called by upcall (D20)

shared immutable: Arc<GameData> (registries), the 'static Blocks/Fluids/Items behaviour tables, config snapshots
off the tick thread: tokio connections, rayon chunk workers and the JVM's other threads, talking to the tick thread over channels (D5, D20)
```

The arenas are server-wide because a Java object's identity does not depend on its level: `ServerPlayer.teleport` moves the same object between levels, and references to it (`Mob.target`, a passenger list) stay valid. Levels own only indices.

- **`EntityKey`** is a `slotmap` generational key: the object identity of an entity, its arena key, and the handle every Rust reference to an entity holds. Java's `int id` (`Entity.getId()`) is *not* the identity: it is a field allocated by the one port of `ServerLevel.ENTITY_COUNTER`/`getNextEntityId()`, it can change (`Entity.setId`, called by `PaperPlayerConfigurationConnection.applyPendingEntityId`), and several objects can share one (`BaseSpawner.SET_DISPLAY_ENTITY_ID` sets every spawner display entity to -1). The `EntityLookup` by-int-id index maps it to a key for packets and `Level.getEntity(int)`; `setId` updates that index.
- **`BlockEntityKey`** is the same kind of key for block entities. Java has no block-entity id; the key is the object identity, so the block entity that replaces another at the same position is a different key, just as Java's `this` and `level.getBlockEntity(pos)` are then different objects.
- **`LevelId`** is a `slotmap` generational key of the server's level arena, never reused, so a stored `LevelId` never names another level; `ResourceKey<Level>` stays the persistent identity. Java's `MinecraftServer.levels` is a `LinkedHashMap` that CraftBukkit's `addLevel` and `removeLevel` replace with a modified copy (`CraftServer.createWorld`, `CraftServer.unloadWorld`). Its port keeps the name and the order: `levels` is an insertion-ordered `ResourceKey<Level> → LevelId` map beside the level arena. A loop over the levels (`getAllLevels()`, `levels.values()`) iterates the id list it reads when it starts, as Java iterates the map it read (rule 6: Java's map is replaced, never mutated), so a world a plugin creates or unloads during the loop does not change the running loop. `removeLevel` removes the key from `levels` at once. The removed `ServerLevel` is then freed as Java's GC frees it, by rule 4's trace: every level in `levels` is a root, and a stored `LevelId` (an entity's `level` field, a Bukkit `World` wrapper) is a pin. So a running loop still reaches the removed level as Java's does (the trace runs only at the end of the tick), a plugin's `World` or an entity it keeps alive still works on it as on Paper's unloaded level, and it is dropped with its outgoing pins by the first trace that does not reach it, after which nothing holds its `LevelId`. An entity's level is its `level: LevelId` field.

## Receivers and handles

Every translated method takes one of two forms.

- **Handle form** `fn m(ctx: &mut LevelCtx, this: H, …)` is used when the receiver lives inside the state `ctx` owns (entities, block entities, levels, the server, components of those) and the Java body, or any override of it, reaches the level, the server or another game object. The body re-borrows the receiver through `ctx` for each group of statements that touches it.
- **Receiver form** `&self` / `&mut self` is used (a) for methods of those same objects whose Java body and overrides touch only the receiver's own fields and the arguments, with no `ctx` parameter, and (b) for objects outside `ctx`: the `'static` block, fluid and item singletons, and values not admitted to the game state (a block entity just built by `newBlockEntity`, `ProtoChunk` contents, locals). Methods in (b) take `ctx` as a parameter wherever Java passes a `Level`.

The compiler polices the split: a receiver-form method of an object inside `ctx` has no `ctx`, so it cannot call a handle-form method. When that bites, the method becomes handle form, decided once on the hub class (ROADMAP R6), never per call site.

**Why not take-tick-putback** (v1 of this file, and PR #767's `level_ctx.rs`): Java routinely reaches the running object through the level. `LivingEntity.hurtServer` resolves `source.getEntity()` (the mob that is mid-`doHurtTarget` in its own tick) and mutates it: `setLastHurtByMob`, then thorns through `EnchantmentHelper.doPostAttackEffects`. A hopper's `setChanged()` calls `Level.updateNeighbourForOutputSignal`, which reaches `ComparatorBlock`, which calls `HopperBlock.getAnalogOutputSignal`, which reads `level.getBlockEntity(pos)`: the hopper that is mid-tick. A receiver moved out of its slot is invisible on those paths, and safe Rust cannot lend `&mut self` back to the level. A handle is what Java's reference is, and re-resolving it on every use is exactly Java's aliasing semantics.

Rules:

1. **No borrow across a `ctx` call.** Read what the Java expression reads into locals, in Java evaluation order, then call, then re-borrow. Java re-reads fields after a call; so does the port.
2. **Dereferencing a handle is not a Java lookup.** `ctx.entity(key)` dereferences a Java reference: it finds any object in the arena, whatever its level, including one constructed but not yet added and one removed but still referenced (rule 4). Java lookups (`Level.getEntity(int)`, `getEntities(except, aabb, predicate)`, `getBlockEntity(pos)` with its creation-type semantics) go through the ported indices with Java's semantics. Never answer one with the other.
3. **Construction and admission.** An entity is constructed into the arena, because Java's constructor takes the level and allocates the id, and Java calls level-touching methods (`snapTo`, `finalizeSpawn` in `NaturalSpawner`) before `addFreshEntity`. Admission (`addFreshEntity`, load, `addDuringTeleport`) inserts the key into a level's `EntityLookup` indices. A block entity is a value until `LevelChunk.setBlockEntity` admits it into the arena; Java calls only receiver-form methods (`loadWithComponents`, `setBlockState`) on it before that. Worldgen threads never touch an arena (§Chunks). Entities that worldgen builds on a worker through `EntityType.create(level.getLevel(), …)` and hands to `WorldGenRegion.addFreshEntity` (`OceanMonumentPieces`, `WoodlandMansionPieces`, `SwampHutPiece`, `EndCityPieces`, `MineshaftPieces`, `EndSpikeFeature`, …) are not decided by this file: those sites stay `STUB` until an OWNERSHIP amendment, landing with the cluster that ports them, settles where such an entity lives while Java finalizes and saves it.
4. **Removal is immediate; freeing is a trace from roots.** `Entity.setRemoved` updates every index in the same call (`levelCallback.onRemove`), as in Java, and Moonrise's iterator-safe tick list keeps the running iteration valid; `LevelChunk.removeBlockEntity` and chunk unload drop a block entity's key from the chunk's index the same way. Freeing stands in for Java's GC and covers the entity, block-entity and level arenas. **A handle stored beyond the current call (in a field of a game object, a component, a connection, a queued task or a scheduled closure) is a pin: an edge from its holder to its target**, recorded by `ctx.repin(holder, old, new)` whenever such a storage location is written. The family scaffold generates the mutators of every Java field whose Rust type stores an entity, block-entity or level handle (a field typed by an entity or block-entity class or by `Level`, a rule-8 handle enum such as `Container`, a `SlotRef`, or a collection of these), so a stored handle cannot skip its pin; a queued task or scheduled closure pins what it captures when it is queued and releases it when it has run or is cancelled. At the end of each server tick the server marks every arena entry reachable from the **roots** along pins and frees every unmarked entry, dropping its outgoing pins. The roots are the levels in `MinecraftServer.levels`, the entries a loaded level indexes (entities in its `EntityLookup`, block entities in its chunks' `block_entities`) and every pin whose holder is not an arena entry: the level-owned state of a level in `levels` (raids, `ServerLevel.dragonParts`, the block-entity ticker list), server-owned state, connections, queued tasks and closures, and live JVM adapter wrappers. The trace may be skipped only in a tick in which no entry left a level's index, no level left `levels`, none was constructed without admission and no pin was released, because then nothing new is unreachable. Because it is a trace, a cycle that no root reaches is freed, as Java's GC collects it: a creeper whose explosion kills the skeleton that shot it leaves each one's `lastHurtByMob` naming the other, and both go in the same sweep; and an owner goes in the same sweep as the objects only it reaches. Sites this keeps alive that the `EntityLookup` never sees include `BaseSpawner.displayEntity` and `TrialSpawnerStateData.displayEntity` (display entities that are never admitted), the eight `EnderDragonPart`s in `EnderDragon.subEntities` (never added to the `EntityLookup`; found through `ServerLevel.dragonParts` and `getEntity(int)`), `connection.savedPlayerForLegacyEvents` (the `ServerPlayer` that `PrepareSpawnTask` builds before admission), every entity a live `CraftEntity` wrapper holds (§JVM adapter boundary), and a broken block entity that an open menu's `Container` handle still names (§Block entities). A Java `WeakReference` field does not pin; its handle dereferences to `None` once the target is freed, which ports `get() == null`. A removed entity or block entity that a reachable stored field still references stays readable with its last state, as in Java, so `isRemoved()` and `isAlive()` read the object's own fields.
5. **No invented queues.** Effects happen in Java order. Deferred structures exist only where Java has them: `Level.pendingBlockEntityTickers` while `tickingBlockEntities`, `EntityTickList`'s `IteratorSafeOrderedReferenceSet`, `ServerLevel.blockEvents`, `LevelTicks`, the `BlockableEventLoop` task queue, and Moonrise's `canRemoveEntity` guard (which drops the removal with a warning, as Paper does). A queue added to satisfy the borrow checker reorders observable effects and is a blocking review finding.
6. **Iterate as Java iterates.** Port the iterator semantics of the Java collection, and re-resolve the collection through `ctx` at each step when the loop body takes `ctx`. An index loop that re-reads `size()` stays an index loop; Moonrise's iterator-safe collections and fastutil's linked collections (whose iterators are *not* fail-fast: `GoalSelector.tick()` walks `availableGoals`, an `ObjectLinkedOpenHashSet`, while goal code can fire `EntityTargetLivingEntityEvent` whose listeners may edit the goals) are ported with their exact iteration behaviour. Iterating a snapshot is allowed only where Java itself iterates a copy (`new ArrayList<>(…)`, `List.copyOf`, `toArray`). Never take a collection or component out of its owner for a loop.
7. **Components.** Owned sub-objects without identity of their own (`GoalSelector` and its goals, `Brain` and its behaviors, `PathNavigation`, the move, look and jump controls, `FoodData`, `Inventory`, `AbstractContainerMenu`, `ServerGamePacketListenerImpl`) live inside their owner. Their Java back-reference (`this.mob`) becomes a field holding the owner's key. A component method that needs `ctx` is handle form with a component handle: the owner's key plus the component's stable key inside the owner (a goal's slot in the selector's ported linked set, the open menu's `containerId`), resolved through the owner on every access (`ctx.mob_mut(this.mob).goal_selector.goal_mut(this.slot)`).
8. **References typed by an interface** whose implementors are game objects become an enum of handles, one variant per implementor family, resolved through `ctx`. `Container` (block entities, container entities, the player inventory, compound containers) is the main case. Item stacks follow Java's own `SlotAccess`: see §Items.

## LevelCtx

`LevelCtx` replaces every back-reference Java code follows to world state: `this.level()`, `level.getServer()`, `this.server`, `level.getCraftServer()`. It is one concrete struct, not a trait, at `rivet_server::server::level::level_ctx`; it has no Java counterpart, and its module doc says so. `ServerCtx` is the same without a current level, for code that belongs to no level: `MinecraftServer`, `PlayerList`, commands, the connection layer.

```rust
pub struct ServerCtx<'t> {
    pub server: &'t mut MinecraftServer,
    pub bridge: &'t PluginBridge,
}

pub struct LevelCtx<'t> {
    pub server: &'t mut MinecraftServer,
    pub bridge: &'t PluginBridge,
    /// Java `this.level()` for the code running now.
    pub level: LevelId,
}

impl ServerCtx<'_> {
    pub fn level_ctx(&mut self, level: LevelId) -> LevelCtx<'_>;
    // handle dereference (rule 2); the same methods exist on LevelCtx
    pub fn entity(&self, key: EntityKey) -> Option<&dyn EntityBehavior>;
    pub fn entity_mut(&mut self, key: EntityKey) -> Option<&mut dyn EntityBehavior>;
    pub fn entity_dispatch(&self, key: EntityKey) -> Option<&'static EntityDispatchRow>;
    pub fn block_entity(&self, id: BlockEntityKey) -> Option<&dyn BlockEntityBehavior>;
    pub fn block_entity_mut(&mut self, id: BlockEntityKey) -> Option<&mut dyn BlockEntityBehavior>;
    pub fn block_entity_dispatch(&self, id: BlockEntityKey) -> Option<&'static BlockEntityDispatchRow>;
    pub fn repin(&mut self, holder: PinOwner, old: Option<PinTarget>, new: Option<PinTarget>); // rule 4, called by generated mutators
    pub fn call_event<E: Event>(&mut self, event: &mut E);
}

impl LevelCtx<'_> {
    pub fn level(&self) -> &ServerLevel;
    pub fn level_mut(&mut self) -> &mut ServerLevel;
    pub fn server_ctx(&mut self) -> ServerCtx<'_>;              // Java level.getServer()
    pub fn in_level(&mut self, level: LevelId) -> LevelCtx<'_>; // Java server.getLevel(key)
    // plus the ServerCtx dereference, repin and call_event methods
}
```

- `PinTarget` is an `EntityKey`, a `BlockEntityKey` or a `LevelId`. `PinOwner` names a pin's holder by its handle: an `EntityKey` or `BlockEntityKey` (an arena entry, whose pins the trace follows only once it reaches the entry; a component's pins are its owner's), a `LevelId` (level-owned state such as raids, `dragonParts` and the block-entity ticker list; a root holder while the level is in `levels`, an arena entry once it is removed), or a root holder: the server (server-owned state), a `ConnectionId`, a scheduler task id, or a JVM adapter wrapper token.
- Typed accessors per hierarchy class (`ctx.living_mut(this)`, `ctx.mob(this)`, `ctx.block_entity_as::<HopperBlockEntity>(id)`) are generated by the family scaffold. Accessors used on `this` panic if the object is gone, because dispatch only reaches live objects and rule 4 keeps removed ones until the tick ends; accessors used on stored references return `Option`.
- The tick loop owns `MinecraftServer` and `PluginBridge` side by side and builds one `ServerCtx` per tick. `MinecraftServer.tickChildren` builds a `LevelCtx` per level for `ServerLevel::tick(ctx)`; packet handling builds one for the player's current level (its `level` field). Only the tick thread ever holds a `ctx`: rayon, tokio and the JVM's other threads never see one (D20).
- A handle-form method whose receiver changes level mid-body (a player in `ServerPlayer.teleport`; Java keeps the same object, and `this.level()` changes) continues with `ctx.in_level(new_level)`. Its key does not change.
- `ServerLevel` and `Level` methods follow the same two forms: those that touch only the level's own fields are `&self`/`&mut self`; those that reach entities, block behaviour, the server or events take `ctx`. Where Java passes the level as one of its interfaces, the implementor is `LevelCtx` itself (§Level interfaces).

**What PR #767's `level_ctx.rs` becomes.** Kept: the Paper-ordered passenger traversal (`tickNonPassenger`/`tickPassenger` with Paper's activation-range `isActive` branch), the preconditions and ordering of `startRiding`, `stopRiding` and `ejectPassengers`, the Moonrise `canRemoveEntity` guard, and int ids starting at 1. Moved: riding and removal become handle-form `Entity` methods in `world::entity::entity`, where Java declares them; the traversal becomes `ServerLevel::tick_non_passenger`/`tick_passenger` in `server::level::server_level`. Deleted: `LifecycleEntity` (replaced by §Class hierarchies), the `IndexMap<i32, Option<_>>` slots keyed by int id with `taken_ids` (take-tick-putback), `pending_removals`/`flush_pending_removals` (Java removes immediately), the `cancel_mount`/`cancel_dismount` flags (`EntityMountEvent`/`EntityDismountEvent` through `call_event`), the `events: Vec<LifecycleEvent>` log (test instrumentation with no Java counterpart; tests observe state, D18), and the separate `NetworkIdAllocator`.

## Level interfaces

Java reaches a level through a family of interfaces: `LevelHeightAccessor`, `BlockGetter`, `SignalGetter`, `BlockAndLightGetter`, `CollisionGetter`, `EntityGetter`, `LevelReader`, `LevelSimulatedReader`, `LevelWriter`, `LevelSimulatedRW`, `CommonLevelAccessor`, `ScheduledTickAccess`, `LevelAccessor`, `ServerLevelAccessor` and `WorldGenLevel`. They have several implementors: `Level`/`ServerLevel`; `WorldGenRegion` (worldgen, on a worker); `PathNavigationRegion` (a `CollisionGetter` built for each path search over the live level); `ChunkAccess` (a `BlockGetter` through `LightChunk`); `EmptyBlockGetter`; and the CraftBukkit `BlockStateListPopulator` (a `DummyLevelAccessor` that Paper's patches pass as the level in `SpongeBlock`, `PortalShape`, `PortalForcer` and `EndPlatformFeature`) and `TransformerLevelAccessor`, both ported as hooks (D16, bucket E). Block code writes, reaches entities and fires events through them: `BlockBehaviour.updateShape(state, LevelReader, ScheduledTickAccess, …)`, `Block.updateOrDestroy` and `updateNeighbourShapes` (`LevelAccessor`), `Block.pushEntitiesUp` (`level.getEntities(…)`, then `teleportRelative` on each entity), `CollisionGetter.isUnobstructed` and `noCollision` (through `getEntityCollisions`). The same body also runs against `WorldGenRegion`: `SculkPatchFeature` reaches `pushEntitiesUp` through `SculkSpreader`.

1. **Traits.** Each interface is a Rust trait with its Java name, Java's super-interfaces as supertraits and Java's default methods as default methods. These interfaces have several Java implementors, so the traits are Java's own seams, not invented ones (PORTING.md).
2. **`&mut` throughout.** A parameter typed by any of them is `&mut dyn X`, and the trait methods take `&mut self`, except the pure members of `LevelHeightAccessor`. A read on the live implementor can change the whole game: `Level.getBlockState` calls `getChunk(x, z, FULL, true)`, a Moonrise sync load that runs main-thread tasks (chunk promotion, entity loading and their events). The `&self` reader traits that `rivet-world` has today take this shape when the cluster that owns each interface lands.
3. **The live implementor is `LevelCtx`**, not `ServerLevel`, because Java's `ServerLevel` bodies of these members reach the server, the arenas and the bridge, which the `ServerLevel` struct does not own. `impl LevelAccessor for LevelCtx<'_>`, and the same for every interface Java's `ServerLevel` implements, holds Java's `Level` and `ServerLevel` bodies. An implementor that wraps another level is a view that borrows it, typed as Java types the wrapped level: `PathNavigationRegion { level: &mut LevelCtx, chunks }` (Java's field is a `Level`; it is built on the tick thread for each path search) with the chunk positions Java captures at construction, and `BlockStateListPopulator { level: &mut dyn LevelAccessorLive, … }` with its captured states, because Java's field is a `LevelAccessor` and one of its sites runs on a worker: `EndPlatformFeature.place` builds it over the `WorldGenRegion` when the `the_end` biome's `end_platform` feature generates, a path Paper's SPIGOT-7746 comment calls asynchronous and on which it fires no event, while `SpongeBlock`, `PortalShape`, `PortalForcer` and the entity path of `EndPlatformFeature.createEndPlatform` build it over the live level (CraftBukkit's `CraftRegionAccessor.generateTree` is adapter code and builds it over whichever level its region wraps). `WorldGenRegion`, `ChunkAccess` and `EmptyBlockGetter` hold only chunk or worker data.
4. **Live members.** The members that need live types (D15: `EntityGetter.getEntities` and `players`; `CollisionGetter.getEntityCollisions` and the defaults that call it, such as `isUnobstructed` and `noCollision`; `LevelAccessor.getServer`, `addFreshEntity` and the `Entity`-taking `playSound`, `levelEvent` and `gameEvent`; `ServerLevelAccessor.getLevel`) cannot be declared on a trait below the live-game crate. When the ledger splits an interface, they sit on the subtrait `<Interface>Live: <Interface>` at the same mirrored path in the live-game crate, whose supertraits also include the `Live` traits of Java's super-interfaces, with `BlockGetterLive` as the root. **Every implementor implements it with its own Java body**: `LevelCtx` with `ServerLevel`'s; `WorldGenRegion` with its own (`getEntities` and `players` return empty lists, `playSound`, `levelEvent` and `gameEvent` do nothing, `addFreshEntity` stores the entity's saved tag in the `ProtoChunk` as `ProtoChunk.addEntity` does); `PathNavigationRegion` with its own (`getEntityCollisions` returns an empty list); and the CraftBukkit hooks with `DummyLevelAccessor`'s and `DelegatedLevelAccessor`'s. In the live-game crate, a parameter typed by a split interface is `&mut dyn <Interface>Live`, so a translated body can call every Java member on it. Below the live-game crate it is `&mut dyn <Interface>`, and code that calls a live member moves up with that member (D15). An interface the ledger places wholly in the live-game crate declares its live members itself.
5. **Reaching handles.** `BlockGetterLive` has one member with no Java counterpart, `fn level_ctx(&mut self) -> Option<LevelCtx<'_>>`. `LevelCtx` returns a reborrow of itself, a view returns its wrapped level's `level_ctx()` (so a `BlockStateListPopulator` over a `WorldGenRegion` returns `None`), and an implementor with no live level returns `None`. It is how a body dereferences a handle obtained through the interface, which Java does by following the object reference: `Block.pushEntitiesUp` takes the keys that `level.get_entities(None, bounds, None)` returns and calls `entity::teleport_relative` with `level.level_ctx()` on each. A value that holds a handle where Java holds the object takes the resolver as a parameter in the members that dereference it: `EntityCollisionContext` stores the `EntityKey` and the fields Java's constructor reads eagerly, and its `getEntity()` and `canStandOnFluid` are resolved through the level the query runs against (`PowderSnowBlock.getCollisionShape` reads `fallDistance` and the boots through it). `None` is reached only where Java's implementor yields no entity (`WorldGenRegion.getEntities` is empty, so the loop body never runs); a `None` on any other path panics and is never answered with a made-up value.
6. **One object, two parameters.** Every Java caller of `updateShape(state, LevelReader level, ScheduledTickAccess ticks, …)` passes the same object twice (`Block.updateFromNeighbourShapes`, `NeighborUpdater.executeShapeUpdate`, `StructureTemplate.updateShapeAtEdge`, `UpgradeData`, Paper's `RedstoneWireTurbo.updateNeighborShapes`), and Rust cannot hold a shared and a mutable borrow of one value. When every Java caller binds two interface-typed parameters to one object, the Rust signature keeps one parameter, typed by the narrowest trait that has both as supertraits and named after the first, and the body uses it for both names: `update_shape(&self, state, level: &mut dyn LevelAccessorLive, pos, …)`. The ledger records the merged signature. If any Java caller binds two different objects, the parameters stay separate.

## Class hierarchies: the dispatch pattern

This applies to every Java class hierarchy with virtual methods: entities, blocks, fluids, items, block entities, menus, goals and behaviors. Java dispatches on the object's runtime class; the port keeps one Rust construct per Java construct.

- **Data.** Each Java class is a struct of its own fields, with its parent embedded as a field named after the parent (`struct Husk { zombie: Zombie }`, PORTING.md).
- **Value trait `<Class>Behavior`** for the root and for every class that has subclasses; its supertrait is the parent's trait, and the root's supertrait is `Any`. It is object safe and holds: generated accessors to the embedded struct at each level (`entity()`, `living_mut()`), generated `as_<x>()`/`as_<x>_mut()` accessors for every class with subclasses and every Java interface in the hierarchy, and the receiver-form virtual methods first declared at that class. Java `instanceof X` is `as_x().is_some()` for those; for a class without subclasses it is an `Any` downcast.
- **Dispatch trait `<Class>Dispatch`**, for hierarchies whose objects live inside `ctx` (entities, block entities), holds the handle-form virtual methods first declared at that class: `fn tick(&self, ctx: &mut LevelCtx, this: EntityKey)`. `&self` is a per-class `'static` marker, not the object. Each concrete Rust struct has one generated `'static` dispatch row, with one `Option<&'static dyn XDispatch>` per hierarchy level, and the value trait returns it (`fn dispatch_row(&self) -> &'static EntityDispatchRow`), so the row travels with the object as Java's class pointer travels in its object header. It is not looked up by `EntityType` or `BlockEntityType`, because the type does not fix the runtime class: `GameTestHelper.makeMockPlayer`, `makeMockServerPlayer` and `makeMockServerPlayerInLevel` build anonymous subclasses of `Player` and `ServerPlayer` that override `gameMode()` and `isClientAuthoritative()`, all with `EntityType.PLAYER`. Such an anonymous class is ported as a named struct in its enclosing class's module (PORTING.md: inner and anonymous classes become nested structs) that embeds its parent and gets its own row. **Block entities** reach their row one step further, because their value trait and structs sit below the live-game crate (§Block entities), where neither can name a row of `&mut LevelCtx` methods: `BlockEntityBehavior` returns a generated class tag instead (`fn block_entity_class(&self) -> BlockEntityClass`, a fieldless enum below with one variant per concrete Rust struct, anonymous-class structs included), and the live-game crate holds the generated `'static` array of `BlockEntityDispatchRow`s indexed by it, which `ctx.block_entity_dispatch(id)` reads. The tag is generated per struct from the same class graph as the rows, so it is the object's runtime class just as a row is, and it is never derived from `BlockEntityType`.
- **Bodies.** The Java body of a method declared or overridden in class X is a free function in X's module: `pub fn tick(ctx: &mut LevelCtx, this: EntityKey)` in handle form, `pub fn random_tick(this: &dyn CropBlockBehavior, …)` in receiver form. Inside a body, a virtual call on `this` always goes through dynamic dispatch (`ctx.entity_dispatch(this)`, `this.get_max_age()`), because that is what Java does when a subclass overrides it; there are no static shortcuts. `super.m()` is a direct call to the parent class's free function.
- **Routing is generated.** For every concrete class, the family scaffold (ROADMAP §2.3) generates the trait impls from the Java class graph: the accessors, the `as_*` methods, and, for each virtual method, the call to the free function of the nearest class that declares it in Java's method resolution order. A missed inherited override silently runs the base body, so routing is never written by hand: it is regenerated from the Java class graph whenever a class in the family changes. Hand-written code is the free functions: the Java bodies.
- **Interfaces** with methods (`EntityBlock`, `Container`, `SimpleWaterloggedBlock`, `BonemealableBlock`, `Leashable`) are traits; the root value trait's `as_<iface>()` returns `Option<&dyn Iface>`.
- **R1 readiness.** All dispatch goes through `'static` trait objects and generated `'static` rows, so a leaf family can move to a higher crate and register its rows (for block entities, its class tags' entries in the row array) at bootstrap without changing a caller.
- There is no `AnyEntity` enum: ROADMAP Batch 3A's "generated `AnyEntity` dispatch (#487)" is this generated routing with its dispatch rows, and the `AnyEntity` enum that `CRATES.md` once described for the entity crate is superseded by it.

## Entities

Java: `Entity` → `LivingEntity` → `Mob` → … (158 entity types in `EntityTypes`). `ServerLevel` ticks them from `entityTickList`, an `EntityTickList` over Moonrise's `IteratorSafeOrderedReferenceSet`, whose iterator never visits entries added during the iteration.

- **Storage.** The server-wide arena maps `EntityKey → Box<dyn EntityBehavior>`; each level's Moonrise `EntityLookup` holds only keys. Boxed, because concrete classes range from `ItemEntity` to `ServerPlayer` (inventories, menus, advancements): an enum would size every slot for the largest. The arena's internal layout is an implementation choice; the `LevelCtx` API is the contract.
- **Traits.** `EntityBehavior`/`EntityDispatch`, `LivingEntityBehavior`/`LivingEntityDispatch`, `MobBehavior`/`MobDispatch`, and so on down every class with subclasses.
- **Tick.** `ServerLevel::tick` walks the ported `EntityTickList` with Java's checks in Java's order (`isRemoved`, `isEntityFrozen`, `checkDespawn`, the vehicle and `hasPassenger` test, `stopRiding`), then `tick_non_passenger(ctx, key)`: `setOldPosAndRot`, `tickCount++`, `totalEntityAge++`, the activation-range `checkIfActive`, then `tick` and `postTick` or `inactiveTick` through the entity's dispatch row, then each passenger through `tick_passenger` (`ServerLevel.tickNonPassenger`/`tickPassenger`).
- **Removal.** `entity::set_removed(ctx, this, reason, cause)` follows `Entity.setRemoved`: the Moonrise guard, the `EntityRemoveEvent` hook, `removalReason`, `stopRiding` when `shouldDestroy`, passengers' `stopRiding` unless `UNLOADED_TO_CHUNK`, `levelCallback.onRemove`, `onRemoval`, then Paper's `retireScheduler()` for a non-player not already removed and not leaving by `CHANGED_DIMENSION` (a plugin-bridge hook: it retires the Folia entity scheduler). All immediate (rule 4).
- **Players.** `ServerPlayer` is an entity like any other: arena entry plus `PlayerList` indices; its connection listener, inventory and open menu are components. Changing dimension moves only index entries from one level's `EntityLookup` to the other's and updates the entity's `level` field; the key and the arena entry stay, because Java keeps the same object.
- **Loading.** Java `EntityType.loadEntityRecursive`/`create` constructs into the arena, runs the receiver-form `load(ValueInput)`, then admits (rule 3).

## Blocks and fluids

Java: `BlockBehaviour` (abstract) → `Block` → about 295 subclasses. `Blocks` constructs one instance per block, in registration order, during static initialization. The fields are final or written once during registration (`Block.defaultBlockState`, `Fluid.defaultFluidState`, `FlowingFluid`'s lazily built state caches, all served by generated tables), except the fields listed under §Mutable singleton state (`RedStoneWireBlock`'s mutable state and `CarvedPumpkinBlock`'s lazily built patterns). `BlockBehaviour.BlockStateBase` delegates as `this.getBlock().m(this.asState(), …)`, and its `initCache` fills per-state caches by calling those methods once.

- **Identity.** The `Block` handle (`rivet-world`) and `BlockState` (`rivet-registry`) stay the only identities. Java `==` on blocks and states is handle equality.
- **Instances.** `'static` immutable singletons (their few mutable or lazily built Java fields are §Mutable singleton state) in one table, built in Java order by the translated `Blocks` registration code, a `LazyLock` as Java's static initializer is. `Blocks` is split (D15): the named `Block` handles stay in `rivet-world`, the registration and table sit in the live-game crate. Lookup is the extension method `block.behavior() -> &'static dyn BlockBehavior` (trait `BlockLive`), because Java's `state.getBlock()` *is* the behaviour object. A startup check asserts table index == generated registry id.
- **Data.** The struct `BlockBehaviour` holds Java `BlockBehaviour`'s instance fields (`properties`, `hasCollision`, `explosionResistance`, `soundType`, `friction`, `drops`, …). Java `Block`'s own fields (`stateDefinition`, `defaultBlockState`, the registry holder, `item`) are served by the generated tables behind the handle, so the embedding chain starts at `BlockBehaviour`: `struct CropBlock { vegetation_block: VegetationBlock }`, `struct VegetationBlock { block: BlockBehaviour }`. A plain Java `Block` instance is a `BlockBehaviour` value.
- **Dispatch.** One root value trait, `BlockBehavior` (named for `Block`, per the `<Class>Behavior` rule), carries the virtual surface Java splits across `BlockBehaviour` and `Block`; `BlockBehaviour` is abstract with `Block` as its only subclass, so they are one dispatch level. Bodies sit in `block_behaviour.rs` or `block.rs`, wherever Java declares them. Everything is receiver form, because `&self` is a static singleton and never inside `ctx`. Java `Level`/`ServerLevel` parameters become `&mut LevelCtx`; parameters typed by a level interface (`BlockGetter`, `LevelReader`, `CollisionGetter`, `LevelAccessor`, `ScheduledTickAccess`, `ServerLevelAccessor`, `WorldGenLevel`, …) become `&mut dyn` trait objects as §Level interfaces specifies, so the same body runs against the live level and against `WorldGenRegion`.
- **Live `BlockState` methods** (`tick`, `randomTick`, `useItemOn`, `entityInside`, `handleNeighborChanged`, …) are the `BlockStateBaseLive` extension trait (D15 split), implemented for `BlockState` in the live-game crate, each delegating as Java does: `self.block().behavior().tick(*self, ctx, pos, random)`. The cached `BlockStateBase` fields stay in the generated tables (`block_behaviors.rs`, dumped from live Paper). The ported virtuals that Java's `initCache` calls must reproduce those tables, checked by a fixture-backed test over all block states (D18 kind 2).
- **Fluids** (`Fluid` → `FlowingFluid` → `WaterFluid`/`LavaFluid`) follow the same pattern, with `FluidState` as the value type, a `Fluids` table and `fluid.behavior()`.

## Block entities

Java: `BlockEntity` (abstract) → about 54 subclasses. `BlockEntityType` holds a factory and the valid blocks. `EntityBlock.newBlockEntity(pos, state)` constructs; `EntityBlock.getTicker(level, state, type)` returns a `BlockEntityTicker<T>`, in practice a static method (`HopperBlockEntity::pushItemsTick`, `AbstractFurnaceBlockEntity::serverTick`) wrapped by `BaseEntityBlock.createTickerHelper`. `LevelChunk` keeps `pos → BlockEntity` and registers each ticker, wrapped in a `RebindableTickingBlockEntityWrapper`, into `Level.blockEntityTickers`; `Level.tickBlockEntities` walks that list by index and removes dead wrappers (Paper's `removeAll` fix).

- **Values.** A struct per class embeds `BlockEntity`. The value trait `BlockEntityBehavior` (load, save, components, `as_container()`, `as_randomizable_container()`, …) and the structs sit below the live-game crate (D15 split), because `ProtoChunk` holds block entities (Java `ChunkAccess.blockEntities`) and worldgen uses them (`RandomizableContainer.setBlockEntityLootTable`; `MonsterRoomFeature` configuring its `SpawnerBlockEntity`).
- **Live interface members.** A Java interface a block entity implements whose members need live types (`Container.stillValid(Player)`, `startOpen` and `stopOpen`, which take a `ContainerUser`) is split as D15 splits interfaces: the members sit on `ContainerLive: Container` in the live-game crate, implemented there for the lower-crate structs, and the class tag's row carries the generated `as_container_live()`/`as_container_live_mut()` accessors that `as_container()` cannot provide below.
- **Arena.** The server-wide `SlotMap<BlockEntityKey, Box<dyn BlockEntityBehavior>>` (§Ownership tree); `LevelChunk` maps `BlockPos → BlockEntityKey` and keeps the Java `HashMap` save order the chunk layer already reproduces. Promoting a `ProtoChunk` moves its values into the arena.
- **Handle-form virtuals** (the ones that reach the level: `setChanged`, `preRemoveSideEffects`, `setRemoved` overrides) go through `BlockEntityDispatch`, found through the row its class tag indexes (§Class hierarchies).
- **Tickers.** `type BlockEntityTicker = fn(&mut LevelCtx, BlockPos, BlockState, BlockEntityKey)`. Java's static ticker methods are handle-form free functions with that signature; the block's `get_ticker` returns `Option<BlockEntityTicker>` through the `createTickerHelper` port. The level's ticker list holds `(BlockEntityKey, BlockEntityTicker)` wrappers with Java's rebinding semantics, each pinning its block entity with the level as owner until `tickBlockEntities` drops it: the existing `LevelBlockEntityRuntime`, holding `BlockEntityKey` instead of a `Weak<()>` identity.
- **Freeing** is rule 4. Breaking a block (`LevelChunk.removeBlockEntity`, which calls `setRemoved`) or unloading its chunk drops the key from the chunk's index at once, and the entry is freed by the first end-of-tick trace that does not reach it. Until then a stored handle keeps it readable: a `ChestMenu` whose `Container` handle names a broken chest keeps that chest until `ChestMenu.stillValid` (`Container.stillValidBlockEntity`, which compares `level.getBlockEntity(pos)` with the chest) fails in `ServerPlayer.tick` and closes the menu, and the ticker wrapper keeps its block entity until `tickBlockEntities` sees it removed.
- This replaces v1's "block entities live in their chunk and tick by take-tick-putback through a `BlockEntityCtx`": the hopper-and-comparator path above needs the ticking block entity reachable through the level.

## Items

Java: `Item` (concrete) → about 70 subclasses. `Items` registers one instance per item; every field is final except `CrossbowItem`'s, listed under §Mutable singleton state. `ItemStack` is a mutable object referenced from slots: `ItemStack.use` calls `this.getItem().use(level, player, hand)`, and item code re-reads `player.getItemInHand(hand)` and mutates that stack in place (`itemStack.consume(1, player)`).

- **Instances.** `'static` immutable singletons (`CrossbowItem`'s mutable fields are §Mutable singleton state) in one table, built in registration order (generated per #186 or translated), looked up by the extension method `item.behavior() -> &'static dyn ItemBehavior` on the `ItemId` handle (trait `ItemLive`, D15 split). The struct `Item` holds only the fields of Java `Item` that the generated tables do not serve (default components come from the generated table); subclasses embed `item: Item`, and `BlockItem` holds a `Block` handle.
- **Dispatch.** The root value trait `ItemBehavior` carries Java `Item`'s virtual methods, all receiver form: `ctx` where Java passes a `Level`, the player or entity as an `EntityKey`, the stack as a `StackRef`.

**Stacks.** `ItemStack` is a value type in `rivet-world` (count, `ItemId`, component patch); its live methods (`use`, `useOn`, `hurtAndBreak`, `inventoryTick`, `finishUsingItem`, …) are the `ItemStackLive` extension trait (D15 split) and take the stack as a handle:

```rust
pub enum StackRef<'a> {
    /// Java's `SlotAccess` / `Container` + index: a stack inside game state.
    Slot(SlotRef),
    /// A stack outside game state (a fresh result, an event record); disjoint from ctx.
    Local(&'a mut ItemStack),
}
```

`SlotRef` names an owner handle plus a slot (an entity's equipment or inventory slot, a block entity's container slot, a menu slot, an item entity's stack) and is resolved through `ctx` at each access, as Java's code re-reads the shared object. Where Java keeps mutating a stack after its slot was overwritten (the stack is now detached), the port moves the stack out into a `Local` at the point Java detaches it.

## Mutable singleton state

A few behaviour singletons carry instance fields that change after registration, measured over every `Block`, `Item` and `Fluid` class and their bases (`BlockBehaviour`, `Block`, `Item`, `Fluid`, `FlowingFluid`) on `0a99345`:

- `RedStoneWireBlock.shouldSignal` (public `boolean`): `getBlockSignal(level, pos)`, and Paper's `RedstoneWireTurbo.calculateCurrentChanges`, set it to `false`, read the neighbour signals and set it back to `true`; `getSignal`, `getDirectSignal` and `isSignalSource(state)` read it, so the wire stops powering itself while it measures its neighbours.
- `RedStoneWireBlock.turbo`, Paper's Eigencraft `RedstoneWireTurbo`: three layer queues, `nodeCache` and `currentWalkLayer`. `updateSurroundingRedstone` is reentered during its own walk (`scheduleReentrantNeighborChanged` merges a nested update into the running breadth-first walk), including from plugin code: `calculateCurrentChanges` fires `BlockRedstoneEvent` (`CraftEventFactory.callRedstoneChange`, `RedstoneWireTurbo.java:892`) mid-walk, and a listener's `setType` with physics reaches the same `turbo`.
- `CrossbowItem.startSoundPlayed` and `midLoadSoundPlayed`, set and reset in `onUseTick` and `use`.
- `CarvedPumpkinBlock`'s six `@Nullable BlockPattern` fields (`snowGolemBase`, `snowGolemFull`, `ironGolemBase`, `ironGolemFull`, `copperGolemBase`, `copperGolemFull`), built on first use by the `getOrCreate*` getters (`CarvedPumpkinBlock.java:162-228`), not during registration, and not served by the generated tables.

Java's instance state of a singleton is per instance and per server: one server per JVM, one `RedStoneWireBlock` (`Blocks.REDSTONE_WIRE`), one `CrossbowItem` (`Items.CROSSBOW`), two `CarvedPumpkinBlock`s (`CARVED_PUMPKIN`, `JACK_O_LANTERN`), each building its own patterns. In Rivet all of a server's game code, plugin code included, runs on that server's tick thread (D20), so none of these fields needs an atomic, an `Arc` or any handoff between threads. Each field takes the first representation that fits, with a comment citing the Java field. Representations 1 and 2 hold one value per class, so the `Blocks` and `Items` registration asserts at startup that each class using them is instantiated once; representation 3 is a field of the instance.

1. **Every reader and writer takes a `Level`** (`turbo`: every `RedstoneWireTurbo` entry point takes `Level worldIn`; `CrossbowItem`'s flags: `use(Level, …)` and `onUseTick(Level, …)`). The field is server-owned game state: a plain field of `MinecraftServer.singleton_fields`, the struct `SingletonFields` in `rivet_server::server::singleton_fields` (a module with no Java counterpart, whose doc says so), named `<class>_<field>` (`red_stone_wire_turbo`, `crossbow_item_start_sound_played`). Bodies reach it through `ctx.server`. A `BlockRedstoneEvent` listener's `setType` runs inside the walk's own `call_event`, on the tick thread, against the `ctx` the walk lent (§JVM adapter boundary), so its nested update finds and extends the running walk, as in Java. Rule 1 applies: the walk re-borrows its queues and `nodeCache` through `ctx` around each statement group and never holds a borrow across a call that takes `ctx`. The ported `RedstoneWireTurbo`'s `wire` field is the `'static` `RedStoneWireBlock` singleton.
2. **Some reader has no route to a level** (`shouldSignal`: `isSignalSource(BlockState)` takes only the state, and `getSignal`/`getDirectSignal` take a `BlockGetter` that can be a `WorldGenRegion` or a chunk). The field is a `Cell<bool>` in a `thread_local!` of the class's module (`red_stone_wire_block::SHOULD_SIGNAL`, initially `true`), read and written with `get`/`set`. It is per server even though it is per thread: every writer takes a `Level` (`getBlockSignal(Level, …)`, `RedstoneWireTurbo.calculateCurrentChanges`), so only a tick thread writes it, and a server's game code runs only on its own tick thread (D20); two servers in one test process tick on two threads, and on one thread the field is `true` again whenever a writer returns. A thread that runs no game code (rayon worldgen workers placing redstone through `WorldGenRegion`, tokio, the JVM's other threads) never writes it and reads `true`, the value Java's field holds outside `getBlockSignal` and `calculateCurrentChanges`: Java's unsynchronized read of the transient `false` from a worldgen thread is a data race, not behaviour, and the constant keeps worldgen deterministic. Nothing installs or clears the slot. A field that representation 1 fits never uses this one, because state reachable through the owner stays with the owner.
3. **A lazily built immutable value** (`CarvedPumpkinBlock`'s patterns). Each field is a `OnceLock<BlockPattern>` in the `CarvedPumpkinBlock` struct, and each `getOrCreate*` getter is `get_or_init` over the Java builder chain. Building has no side effects and the built pattern is immutable (its predicates read block states and tags when it matches, not when it is built), so when it is built is unobservable. Building eagerly at registration would be equally unobservable, but `OnceLock` keeps Java's getter structure; it is a lock rather than a plain field because the singleton is `'static` and shared with worldgen workers.

A new mutable or lazily built field on a singleton in a later Paper version joins this list by an OWNERSHIP amendment, in one of these three representations.

## Chunks
Chunks owned by `ChunkMap` by value. Block state = palette index into generated global state table (`rivet-registry`), copy `u32`-ish IDs, no references. Block entities are indexed by the chunk and owned by the server-wide block-entity arena (§Block entities). Chunk gen/lighting runs on `rayon` on detached `ProtoChunk` values, results merged into `ChunkMap` on the tick thread via channel; worker threads never touch an entity or block-entity arena or a `LevelCtx`.

The chunk *pipeline* — ticket levels and holder lifecycle, the `ChunkStatus` generation DAG and radii, chunk send ordering, storage-worker/write ordering, cancellation/backpressure, and the determinism-under-parallelism invariants — is specified in `docs/chunk-pipeline-spec.md` (issue #185). Tick-thread ownership (§5 there) is the realization of this section's rule; the Moonrise scheduler internals (executors, propagation engine) are deliberately deferred to that issue.

`ChunkPos`/`SectionPos` live in `rivet-registry::core` as pure value types, resolved by ID — `ChunkPyramid.MAX_CHUNK_COORDINATE_VALUE` moves to a `const` there so `ChunkPos` stays value-only. (Java puts `ChunkPos` in `world.level`; the module mirror is a convenience and cycle-breaking justifies the one-line move.)

## Chunk storage workers (region files) — storage-worker amendment

Issue #231 amendment (the `world.level.chunk.storage` slice). Region-file IO is **not game state**: `RegionFile`/`RegionFileStorage`/`IOWorker` are owned handles on the chunk-IO side (rayon/tokio worker pools), never stored inside `ChunkMap`. The tick thread hands **owned `CompoundTag` values** across the channel boundary — no `Arc<RwLock>` on chunk data anywhere on this path.

- Per-`RegionFile` mutual exclusion (Java `synchronized` on `write`/`getChunkDataInputStream`) maps to a `Mutex<RegionFile>` held by the region's single IO task, or a region-keyed single-writer queue (`chunkX >> 5, chunkZ >> 5`). This cross-thread IO lock is explicitly inside the "cross-thread queues only" exception below — a worker/queue mutex, never a lock on game state.
- Chunk ownership is unchanged: the chunk is owned by `ChunkMap` by value; `SerializableChunkData` builds/reads a plain value `CompoundTag` on the worker side. Starlight light arrays survive load→save as opaque bytes in the compound — no engine, no shared state.
- Value types: `ChunkPos` (region math `& ~31`, `getRegionLocalX/Z`, `pack`) is a `Copy` value type; `RegionStorageInfo` is a `Clone` value type (it owns `String`/`ResourceKey` fields, so it cannot be `Copy`). Java's `info.dfuType()[0] = dataFixType` mutable-array hack becomes a plain `is_chunk_data: bool` field — do not reproduce a shared-mutable array.
- Codec selection is a frozen value: the `RegionFileVersion` chosen by `configure` is shared freely like `GameData`; the gzip/deflate/lz4 stream wrappers are pure functions over `Read`/`Write`.
- `RegionBitmap` is an owned `BitSet`-equivalent inside each `RegionFile` — sector allocation is per-file derived state, never global.

## Network
Per-connection tokio task owns the socket, encryption, and framing; decoded packets flow to the tick thread over bounded channels keyed by `ConnectionId`; outbound is the reverse. Handshake/status/login handled entirely on the tokio side; play-state packets are game state and cross to the tick thread. Packets are plain owned structs — no lifetimes in packet types (accept the copies; optimize later with `bytes::Bytes` for blobs).

## Registries, tags, recipes

Loaded/generated at startup, frozen, `Arc<GameData>` shared everywhere including
worker pools. Interior mutability forbidden after freeze.

Registry model (decided #107, implemented in rivet-registry):

- **One concrete `Registry<T>`** (no trait): owns `Vec<T>` by insertion order
  (append-only; **element id == holder id == network id == insertion index**),
  plus `by_location`/`by_key` (`FxHashMap<_, u32>`). `DefaultedRegistry` is
  `Option<u32> default_id` with its asymmetric fallbacks preserved. Frozen
  registries are immutable value tables.
- **Builder → freeze:** mutable `RegistryBuilder<T>` (pre-freeze `register`,
  `get_or_create_holder`, `create_intrusive_holder`, `bind_tags`) is consumed by
  `freeze()` → `Registry<T>`; `freeze()` panics with sorted unbound keys like
  `MappedRegistry.freeze()`. The `frozen` boolean + `validateWrite()` are
  compile-time (phase types), not runtime checks.
- **`Holder<T>` is an ID, not a value:** `Direct(T)` (unregistered, decode-only)
  or `Reference{ registry: RegistryId, id: u32 }` (Copy, 8 bytes). All
  `holder.value()/is(tag)/key()/tags()` resolve through the owning
  `&Registry<T>` / `&HolderLookup<T>` — OWNERSHIP's back-reference rule. No
  stored `Arc`/`&Registry` in game state (FFI marshal IDs).
- **Registry identity is `RegistryId` (a per-instance u32), distinct from the
  `ResourceKey<Registry<T>>` key** — one key can have many instances (per-world
  registries); holder serialization-owner checks compare `RegistryId`.
- **`ResourceKey<T>`/`TagKey<T>` are value types** (`PhantomData<fn() -> T>`,
  no `T` bound on Eq/Hash). Java's weak interning makes its `==` equivalent to
  value equality; Rust derives it. No interning, no pointer comparisons.
- **Heterogeneous registry sets (`RegistryAccess`, the ROOT registry) use
  `trait AnyRegistry: Any` + `Box<dyn AnyRegistry>`**, downcast at those two
  erased boundaries only.
- **Reload = rebuild + swap:** datapack reload builds a fresh `Registry`/
  `GameData` (via `RegistrySetBuilder.buildPatch`) and atomically replaces the
  old. No in-place tag rebind on frozen registries; code holding a `&Registry`
  across a reload sees the old table (document per site).
- **Protocol codecs live in `rivet-protocol`, never `rivet-registry`:**
  `StreamCodec` impls for Identifier/ResourceKey/TagKey/Holder/HolderSet live in
  `rivet-protocol`. The pure value types (BlockPos/Vec3i/SectionPos/UUIDUtil/
  Direction/GlobalPos/BlockBox/Rotations) stay in `rivet-registry::core`, with
  only their `StreamCodec` impls crossing to `rivet-protocol`. The network-sync
  `RegistrySynchronization` and `ClientAsset` (both `net.minecraft.network.codec`-
  dependent) move to `rivet-protocol` outright. Dependency direction:
  `rivet-protocol → rivet-registry`; `rivet-registry` never depends on
  `rivet-protocol`.
- `GameData` owns the provider; `Level` may hold a per-dimension provider
  (layer order STATIC → WORLDGEN → DIMENSIONS → RELOADABLE is observable —
  keep an explicit ordered vec).

## Events and the plugin bridge

Java: Paper's patches fire Bukkit and Paper events at fixed points in NMS code, either through CraftBukkit helpers (about 470 `CraftEventFactory` calls in about 250 files, measured on `0a99345`; the most frequent are `callEntityChangeBlockEvent`, `callBinaryRedstoneChange`, `handleBlockGrowEvent` and `handleBlockSpreadEvent`) or by building the event inline and calling `event.callEvent()`/`PluginManager.callEvent` (about 420 sites). `PaperEventManager.callEvent` dispatches synchronously, on the main thread, to the event's `HandlerList`, and the call site then reads the event back (`isCancelled()`, modified fields). Some helpers carry game logic: `handleBlockGrowEvent` places its `CraftBlockState` snapshot (`snapshot.place(flags)`) when the event is not cancelled. A few sites skip work when no listener is registered (`getHandlerList().getRegisteredListeners().length == 0`, in hoppers and signs).

1. **Call sites are translated in place**, in Java order relative to the surrounding game-state changes.
2. **`CraftEventFactory` helpers** reached from translated code are ported, with their Java names, to `rivet_server::bukkit::craftbukkit::event::craft_event_factory` (the D15 path of `org.bukkit.craftbukkit.event.CraftEventFactory`); the block-state snapshot logic they use (`CraftBlockStates.getBlockState`, `CraftBlockState.place`, including its block-entity copy) goes to `rivet_server::bukkit::craftbukkit::block`. Their game-state logic is ported exactly (D16, bucket E); the Bukkit wrapper objects (`CraftBlock.at`, `getBukkitEntity()`, `asBlockData()`) are replaced by handles. Inline event sites stay inline.
3. **Event records.** Each Bukkit or Paper event class that translated code fires gets a Rust struct with the Java class name, in the live-game crate at the D15 path of its Java class (`org.bukkit.event.block.BlockGrowEvent` → `rivet_server::bukkit::event::block::BlockGrowEvent`; Paper's `io.papermc.paper.event.…` → `rivet_server::papermc::paper::event::…`). It is a port of the event class's state and of every member the call site reads back, with Java's constructor defaults and derived getters, because those carry behaviour even with no listener: `PlayerInteractEvent.isCancelled()` is `useInteractedBlock() == DENY`, its constructor sets `useClickedBlock` to `DENY` when there is no clicked block, and `setCancelled` rewrites both results; `EntityDamageEvent.getFinalDamage()` sums the modifiers. Values hold handles and owned values (`EntityKey`, `(LevelId, BlockPos)`, `BlockState`); a stack that Bukkit exposes as a live mirror of a slot (`CraftItemStack.asCraftMirror`) is a `SlotRef`, not a copy, so a plugin edit reaches the slot as in Paper. `trait Event { const TYPE: EventType; }`, with `EventType` a generated enum, is the marshalling key, not a gameplay seam.
4. **`LevelCtx::call_event(&mut self, event: &mut E)`** is `PaperEventManager.callEvent`. If the bridge reports no listener for `E::TYPE`, it returns: building the Bukkit wrappers has no game-state effect, so skipping them is unobservable. Otherwise `PluginBridge::dispatch` makes the upcall from the tick thread and lends the whole `LevelCtx` to it until the last handler returns (§JVM adapter boundary), and the call site then reads the record back. Paper's explicit no-listener checks become `ctx.bridge.has_listeners(EventType::X)` at the same sites.
5. **Plugins touch game state only inside a lent `ctx`**: during an event dispatch, during the scheduler heartbeat (`MinecraftServer.tickServer` → `mainThreadHeartbeat`), and during plugin lifecycle calls. Every plugin-side operation resolves ids through that `ctx` and may fire nested events, as Bukkit's reentrant `callEvent` allows. No game state sits behind a lock, a queue or an `Arc`.
6. **`PluginBridge`** is owned by the tick loop beside `MinecraftServer` (Java's `CraftServer` is adapter code, D16) and lent as `&PluginBridge` in every `ctx`. It holds the listener registry (listener presence per `EventType`, native handlers), the JVM adapter handle and no game state; that is what makes lending it shared next to `&mut MinecraftServer` sound. The registry sits in a `RefCell` that only the tick thread touches (D20) and is borrowed only to copy the handler list before invoking it, as Bukkit's `HandlerList` bakes its array, so a handler may register or unregister listeners mid-dispatch and the change applies from the next `callEvent`, as in Bukkit.
7. **Asynchronous events** (`Event.isAsynchronous()`: `AsyncPlayerPreLoginEvent`, `AsyncChatEvent`, …) are dispatched from the thread Paper uses, with owned data only and no `ctx`, never through the tick thread's `rivet-ffi` runtime; the tick thread consumes their results where Paper does, and a listener's calls that reach game state follow D20.
8. **Bukkit state that Paper persists in NMS saves** (`PersistentDataContainer` → `PublicBukkitValues`) is a field of the Rust entity or block entity, not adapter state.
9. **Before P3** the bridge has no plugin runtime and `has_listeners` is always false; every hook still runs its game logic.

## JVM adapter boundary

Plugin code runs on the tick thread (D20). The JVM is in-process; `PluginBridge::dispatch`, the scheduler heartbeat (`mainThreadHeartbeat`), command execution and plugin lifecycle calls are FFM upcalls made from the tick thread, and Java runs on the tick thread only inside such an upcall. Each upcall lends the `ctx` of the frame that makes it for the duration of the upcall: `rivet-ffi` records it in the tick thread's runtime state (#772) and every shim downcall made during the upcall reborrows it on the same thread, so a Bukkit setter or a nested event runs translated game code against that `ctx`, exactly as a Paper plugin calls into NMS on the main thread. A nested event lends the reborrow to a nested upcall, so the lent `ctx`s form a stack that unwinds as the upcalls return. The reborrow (a pointer to a `ctx` whose owning frame is suspended in the upcall and does not touch it until the upcall returns) is the adapter's one `unsafe` borrow, confined to `rivet-ffi`. A downcall from any other thread returns `WrongThread` and touches no game state; the shim turns that into what Paper does off its main thread (D20). `rivet-ffi` has one entry point that any thread may call: it posts a request (a marshalled call, a pin release) onto `MinecraftServer.processQueue`, the cross-thread queue (`Mutex`, §Allowed shared-state exceptions) that the tick thread drains where Paper drains it, and touches no game state itself. Plugin worldgen code that Paper runs on a worldgen worker against that worker's chunk (a custom `ChunkGenerator` through `CustomChunkGenerator`, a `BlockPopulator` or structure transformer over a `LimitedRegion`, `AsyncStructureGenerateEvent`) reaches no tick-thread state; its FFI surface over the worker's `ProtoChunk` and `WorldGenRegion` is not decided here and needs a D20 amendment before P3 ports it.

FFI handles for game objects are the arena keys themselves, marshalled as `u64` words (D11): an entity is its `EntityKey` and a block entity its `BlockEntityKey` (`KeyData::as_ffi`: slot and generation, the same `(slot, generation)` shape `rivet-ffi`'s `GenerationalTable` already uses); a world is its `LevelId`; a block is two words, `LevelId` and `BlockPos.asLong()`; a stack is the words of its `SlotRef`. For game objects the arenas are the handle table, and D11's per-call re-resolution is an arena lookup through the lent `ctx`, and a stale key (an entity, block entity or level that is gone) resolves to `HandleStale`, never to another object; `rivet-ffi`'s own `GenerationalTable` keeps the handles that are not game objects (runtimes, callback tokens) and, until the live game exists, the entity handles of its ABI tests. Pointers into arenas never cross the boundary.

Bukkit lets a plugin keep an `Entity` and read it after the entity died, because the `CraftEntity` retains the NMS object. The adapter therefore pins (rule 4) every entity that a live `CraftEntity` wrapper references, with the wrapper's token as the pin owner, and releases the pin when the wrapper is collected (the `java.lang.ref.Cleaner` runs on a JVM thread of its own and posts the release through that any-thread entry point), so a dead entity's last state stays readable exactly as long as Paper would keep it.

## Allowed shared-state exceptions
`Arc`: registries/GameData, config snapshots, the connection registry. `'static` immutable: the `Blocks`, `Fluids` and `Items` behaviour tables and the generated dispatch rows. `OnceLock`: the lazily built immutable singleton fields of §Mutable singleton state. `Mutex`: cross-thread queues only. `Cell`/`RefCell`: bookkeeping that is not game state and that only the tick thread touches (the plugin bridge's listener registry). `thread_local!`: the representation-2 fields of §Mutable singleton state (written only on the tick thread) and `rivet-ffi`'s thread-confined runtime table (#772), which holds no game state. Anything else needs an OWNERSHIP.md amendment PR first.
