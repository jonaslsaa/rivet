# Rivet verification plan

Scope: how we know, continuously and cheaply, that ported code behaves like Paper 26.2 (`0a99345`).
Not a roadmap. Measured on `main` @ `4fc14eeb` (2026-11-23). Numbers marked *(est.)* are estimates;
everything else was counted from the tree.

How the counts were made: LOC = lines of `crates/**/*.rs` excluding `generated/` and the two big
tables (`unicode_name_table_generated.rs`, `mth_sin_table.rs`), inline tests included. "Fixture-backed"
= the file references a fixture path / `include_str!` / `include_bytes!`. This is a file-level grep, so
it is a heuristic: it over-credits files that include non-Java data and under-credits tests whose
Java-derived constants are pasted inline. Treat the percentages as +/-10 points.

---

## 0. Bottom line

1. **What exists is deep but narrow and bespoke.** 93 Java probes (14.9k Java LOC), 90 probe scripts,
   6,131 committed fixture files, 5 live codegen probes, a JSON-lines Java reference oracle with 5 ops,
   and 2 real Paper-vs-Rivet bot differentials (join, move). Each new surface costs a hand-built probe,
   a shell script, a JSONL file and a Rust test. That does not scale with port throughput.
2. **Most ported code has never been compared to Paper.** 493k ported LOC; 1,351 source files; only
   125 files reference a fixture. Of ~5,950 tests, ~17% sit in fixture-backed files, ~22% in files that
   at least mention an oracle/golden, ~60% in files with no Java provenance at all. At least 116k LOC
   live in module buckets with **zero** Java-sourced fixtures (entity, items, crafting, loot,
   enchantment, effects, inventory, trading, scores, brigadier, carvers, api, gametest).
3. **The whole-system comparators are off.** `verify-generated-full` and the Paper-vs-Rivet
   `hash-diff` are opt-in (`RIVET_GENERATED_FULL`, `RIVET_HASH_DIR`) and inactive; `generated-world`
   is pinned UNVERIFIED. So ~125k LOC of worldgen is verified only at isolated checkpoints for seed 42.
4. **Committed goldens are trusted, not re-derived.** No gate step re-runs the 90 oracle probes. A
   hand-edited or stale JSONL is undetectable. Only the codegen data (5 probes) and the M0/M2 region
   baselines are regenerated against live Paper.
5. **The scoreboard is stale and partial.** `PARITY.md` was last refreshed 2026-08-09 and has 5 rows
   (NBT + text). 3.5 months of porting are not on it.
6. **The upstream GameTest corpus does not exist.** At the pinned commit the only bundled test
   instance is `minecraft:always_pass` (issue #24 audit, confirmed in
   `working/Paper/paper-server/src/minecraft/resources/data/minecraft/test_instance/`). GameTest gives
   us a runner and an arena format, not a behavioral suite. Plan accordingly.

The fix is not "more probes". It is: one generic oracle seam that makes a new verification surface
cost ~30 lines of Java, one ledger that maps every ported file to the row that verifies it, and a
debt number that stops porting when it grows.

## 2. Verification architecture

### 2.1 One seam: the oracle op

Today there are two Java mechanisms: one-shot probes (compile a class against the Paper jar, emit
JSONL, commit) and the long-lived reference oracle
(`/home/jonas/Rivet/tools/rivet-reference-oracle/src/RivetReferenceOracle.java`, JSON-lines
request/response, 5 ops). Unify on the second.

An **oracle op** is:
- a named Java handler that runs real Paper classes on a request (`{"op":"loot.roll","table":...,"seed":...}`),
- a Rust handler producing the same response from Rivet code,
- an input corpus: committed, or produced by a seeded generator (seed committed),
- a comparator (default: byte equality of canonical response JSON) and at least one tamper negative.

Each op runs in two modes from the same code:
- **record** — run the corpus through Paper, write `fixtures/ops/<op>.jsonl` plus a manifest
  (Paper commit, op source SHA-256, corpus SHA-256, output SHA-256). Cargo tests consume the JSONL.
  This is the offline tier: it runs in every scoped gate with no JVM.
- **live** — boot the oracle once, stream the corpus (and optionally a larger seeded corpus) through
  both sides, compare directly. This is the oracle tier. One JVM boot serves every op.

Record mode re-run in the nightly tier must reproduce the committed JSONL byte-for-byte. That closes
gap 4 (hand-edited or stale goldens) for every op at once.

Existing probes are not rewritten. They get wrapped: a table `probes.tsv` (script, output path) and a
single `rivet-oracle regen --check` that runs each script into a temp dir and byte-diffs. New surfaces
are written as ops. A probe is migrated to an op only when someone has to touch it anyway.

Why this is the long-term shape and not a stopgap: generic ops verify whole registries with no
per-class Java. Three examples that each cover tens of thousands of LOC:

| Generic op | Java side (approx.) | Covers |
|---|---|---|
| `packet.reencode(state, dir, id, bytes)` | Look up the `StreamCodec` in `ProtocolInfo`, decode, re-encode, return bytes or the rejection class. ~40 lines. | All 227 packet types. Rust encodes arbitrary instances (the fuzz `Arbitrary` impls exist), Paper must decode and re-encode to identical bytes; Paper-captured bodies must do the same through Rust. |
| `codec.reencode(codec, ops, payload)` | Named map of `Codec<?>` constants (ItemStack, DataComponentPatch, LootTable, Recipe, Enchantment, BlockState, ...), parse under `NbtOps`/`JsonOps` with registry access, encode back. ~60 lines + one line per codec. | `rivet-serialization` plus every data-driven type in items/loot/crafting/enchantment/worldgen settings. Accept/reject parity included. |
| `registry.eval(kind, key, input)` | Per kind: `feature.place`, `loot.roll`, `recipe.match`, `structure.start`, `enchant.select`. One handler per kind, iterated over **every entry of the vanilla registry**. | Feature fan-out (57k LOC), loot (5.3k), crafting (5.8k), structures (14.5k), enchantment (4.1k). |

### 2.2 Layers

| # | Layer | Catches | Cost | Tier |
|---|---|---|---|---|
| L0 | Static: fmt, clippy, marker audit, machete, manifest suite | Hygiene, stale stubs | seconds-minutes | scoped |
| L1 | Recorded goldens (ops in record mode, legacy probes, codegen data) consumed by `cargo test` | Regressions in pure functions, codecs, tables | free at test time | scoped |
| L2 | Live ops through the reference oracle, incl. registry-wide sweeps and seeded random inputs | Divergence on inputs nobody thought to record; accept/reject parity | 1 JVM boot (~10 s) + ms per check | oracle |
| L3 | World-state differential: per-status chunk checkpoints and FULL chunk `xxh3_64` hash-diff | Any worldgen/lighting/serialization divergence, end to end | minutes per seed-region | oracle (Stage A), nightly (Stage B/C) |
| L4 | Arena tick-trace differential: same structure + script on both servers, no client, state snapshot every tick | Ticked gameplay: fluids, scheduled ticks, block entities, redstone, pistons, entity physics, AI | ~1 JVM boot per batch of arenas | oracle |
| L5 | Client-observable differential: Azalea bot against Paper and Rivet | Network glue: packet order and content, server corrections, session lifecycle | 20-60 s per row | oracle, hard cap ~12 rows |
| L6 | GameTest pass/fail on both servers | Runner semantics; author-asserted invariants | rides on L4 arenas | oracle |
| L7 | Differential fuzzing (L2 ops driven by libFuzzer / seeded sweeps), time-boxed | Decoder edge cases, panics, accept/reject drift | fixed budget (e.g. 20 min) | nightly |
| L8 | Paper JUnit against the adapter; plugin corpus smoke | API surface and shim behavior | minutes | M4 onward |

Opinionated calls:

- **L2 is the workhorse.** It is the only layer whose marginal cost per ported unit is near zero.
  Default answer to "how do I verify this unit" must be "which op covers it", not "write a probe".
- **L4, not the bot, carries gameplay.** Bot scenarios are slow, wall-clock driven and can only see
  what the client sees. Server-side traces are tick-indexed (no alignment problem), see everything,
  and batch dozens of arenas per JVM boot. Keep L5 for the handful of flows where the packet stream
  *is* the behavior (join, move, dig/place, container click, melee hit, chunk streaming, respawn).
- **GameTest is an arena container and a runner to be verified, not a corpus.** No upstream tests
  exist. Author arenas as structure templates (and, where useful, `block_based` test instances, which
  are pure data). Admission rule: an arena is accepted only if Paper runs it deterministically twice.
  The trace diff is the oracle; GameTest pass/fail is a weaker second signal on the same arena. Do not
  wait for the 47-file runner port to start L4 — the trace harness needs structure placement and
  `tick()`, which exist.
- **Do not port Paper's JUnit to Rust wholesale.** 9,136 of 9,653 tests are paper-server registry/Craft*
  consistency checks. Their natural target is the Java shim layer at M4, run unchanged in the JVM. The
  census (`tools/paper-junit-baseline`) already gives the denominator. Until then the honest scoreboard
  row is `0 / 9,653`. Port a JUnit class to Rust only when it tests a class that has a direct Rust
  twin (e.g. `rivet-registry/tests/position.rs`).
- **No golden-master of Rivet's own output.** A snapshot recorded from Rivet is a hand-written
  expectation with extra steps. Every expected value has a Paper commit and an op/probe SHA in its
  manifest, or it does not count toward verification.

### 2.4 Comparison and normalization

One comparator, used everywhere:
1. Both sides emit **canonical JSON lines**: keys in a fixed order defined by the op, integers as
   integers, floats as raw IEEE-754 hex bits (`Float.floatToIntBits` / `Double.doubleToLongBits`,
   which canonicalize NaN per D14) with an optional decimal alongside for humans.
2. Comparison is byte equality per line. First divergence is reported with op, input id, and a
   field-level diff. Raw outputs from both sides are kept under `tools/rivet-oracle/work/` for triage.
3. **Exclusions are data, not code.** A committed table per comparator: field path, reason, issue link.
   A field is excluded only when Paper differs from itself across twin runs. Review rejects any
   exclusion added in the same PR as the port it would excuse.
4. **Every comparator has a tamper negative** (the existing convention: `--expect-fail`, `--mutate`,
   `--tamper`). A row without a detected negative is UNVERIFIED, not PASS.
5. **Closure is checked**: declared corpus count == executed count; zero executed is UNVERIFIED. This
   is already how `rivet-parity` behaves; make it the shared library behavior in `rivet-harness-common`.

### 2.5 Nondeterminism

| Source | Handling |
|---|---|
| World seed | Committed seed list; both sides read the same file (already the #175 rule). |
| `RandomSource.create()` / `RandomSupport.generateUniqueSeed()` (time + static counter) | **Seed-injection contract.** The Java arena probe reseeds after construction: `level.random`, `level.getThreadSafeRandom()`, and each entity's `random` at spawn, with `mix(scenarioSeed, siteId, spawnOrdinal)`. Rivet exposes the same injection points behind a test-only constructor argument (never a global). The list of injection sites is a committed table; a site not on the list means the arena must not exercise it. Start with RNG-free mechanics (fluids, scheduled ticks, redstone, pistons, hoppers) so the harness lands before this contract is complete. |
| Random ticks, natural spawning, weather, daylight | Off by default in every arena (`randomTickSpeed 0`, spawn limits 0 via the existing `paper-world-defaults.yml`, weather/daylight gamerules off). An arena opts in explicitly and then depends on the seed contract. |
| Tick alignment | L4: none needed, both sides are driven by tick count from the same initial state. L5: transcripts are indexed by server tick and by causal order (packet N after ack M), never wall-clock; wall-clock values are compared only as thresholds (dwell). |
| Threads | Paper pinned to 1 worker / 1 IO thread with the boot log asserted (exists, #266). Rivet: results must be identical at rayon threads = 1 and default; that pair is itself a nightly row. |
| Entity IDs (static `AtomicInteger`) | Fresh JVM per batch plus first-appearance renumbering in the normalizer. |
| UUIDs | First-appearance renumbering unless derived deterministically (offline player UUIDs are, and are compared exactly). |
| Hash-map iteration order | If the order is observable in Paper (NBT bytes, packet order), it is compared exactly and Rivet must reproduce it (D12 precedent). If Paper's order is unspecified *and* differs across Paper twin runs, compare as a sorted set and record the exclusion. |
| Timestamps (`LastUpdate`, `LastPlayed`, file mtimes) | Normalized to 0 with a named exclusion (exists). |
| Floats | Bit-exact, NaN canonicalized (D14). No epsilons anywhere. |
| JIT / platform | x86_64 + Temurin 25 only, as D14 already pins. |

Admission rule for any new row (generalizing what join/move already do): **Paper-vs-Paper twin runs
must be byte-identical after normalization before the Paper-vs-Rivet comparison counts.**

## 3. Gating policy

### 3.1 The ledger

One committed file, `VERIFY.tsv`, is the source of truth. One row per verification surface:

`id · layer · rust_globs · java_classes · mechanism (op/probe/scenario) · corpus_n · negative (y/n) · tier · status · matched · mismatched · last_verified_commit`

- `rust_globs` maps source files to the row that verifies them. A file may be covered by several rows.
- `status` is one of `PASS`, `FAIL`, `UNVERIFIED`, `INACTIVE`. Only the tool writes status and counts.
- `PARITY.md` is rendered from the ledger by `rivet-parity --scoreboard` and is never hand-edited.
  (Today it is rendered from 5 hard-coded checks plus a hand-written M1 section.)

### 3.2 Tiers

| Tier | When | Contents | Budget |
|---|---|---|---|
| **T0 scoped** | Every PR, in its worktree, by the workflow | fmt/clippy/nextest for touched crates (includes all L1 goldens), marker audit, `verify-ledger --check` on the diff | under 10 min warm |
| **T1 merge** | Every merge, serialized under the build lock | T0 workspace-wide + codegen drift + ledger monotonicity + **path-triggered oracle rows** (rows whose `rust_globs` intersect the diff) + the always-on cheap rows (`rivet-parity`, live ops: one JVM boot) | under 20 min typical |
| **T2 full oracle** | Every batch (at most 5 merges or 24 h, whichever first) and before any milestone/epic close | Everything: all Paper boots, all scenarios, all arenas, Stage A hash-diff, harness self-checks, `--require-oracle` | whatever it takes; ~30-45 min *(est.)* |
| **T3 nightly** | Once per day, unattended | T2 + `regen --check` of every probe and op + Stage B/C seeds + differential fuzz (time-boxed) + rayon 1-vs-default determinism | 1-3 h, off the merge path |

No row is ever dropped from T2. Tiering changes *when* a row runs, never *whether*. This amends D10
("full gate on every PR") and therefore needs its own DECISIONS.md PR; the argument is that the six
Paper-vs-baseline boots and eleven capture boots cannot detect a Rivet regression in a PR that does
not touch their inputs, and running them per merge is what makes verification feel expensive.

A red T2 or T3 freezes merges of port PRs. The only allowed work is the fix or a revert. Bisect cost
is bounded by the batch size and by path-triggering (the failing row names its globs).

### 3.3 What every PR must show

1. **T0 green**, evidence pasted (commands + counts), produced at the exact head.
2. **Coverage declaration.** For every new or materially changed `crates/**/src/**.rs` file, the PR
   either (a) is matched by a ledger row whose mechanism is Java-sourced and whose status is `PASS`
   after this PR, or (b) adds the row in the same PR, or (c) is preceded by a merged verification PR
   that added it as `UNVERIFIED` (test-first: the row exists and fails/blocks until the port lands), or
   (d) registers the file as debt with an owning issue. (d) is legal only while the subsystem is under
   its debt threshold (section 4).
3. **Provenance for new expectations.** Any new assertion whose expected value is a literal computed
   by Paper must cite the op/probe and input that produced it. Reviewers reject expected values with
   no provenance on serialization, math, RNG, worldgen, and tick-order surfaces. Hand-written tests are
   still welcome for ownership invariants, error handling and Rust-only seams, but they earn zero
   verification credit.
4. **No fixture, golden, exclusion table, or comparator edit** in a port PR. Those change only in
   verification PRs, and a fixture change must be reproducible by `regen`.
5. **No scoreboard regression** (below).

Preferred ordering for the controller: *verification PR first, port PR second*. The op and its
recorded goldens land while the Rust side is a `STUB`; the ledger row is `UNVERIFIED`; the port PR
flips it to `PASS`. This makes "done" observable and keeps implementers from tuning tests to their own
output, because the expectation predates the implementation.

### 3.4 Scoreboard computation and monotonicity

- Per row: `inputs` (declared corpus), `matched`, `mismatched`, `status`. Rendered grouped by subsystem
  with a per-subsystem verified-LOC percentage from the debt script.
- The gate regenerates the scoreboard and compares with the committed one on `main`:
  - a row may not disappear;
  - `inputs` may not decrease;
  - `matched` may not decrease;
  - `status` may not move away from `PASS`;
  - `mismatched` may not increase;
  - verified-LOC percentage per subsystem may not decrease by more than the PR's own registered debt.
- Adding a row that is `FAIL` or `UNVERIFIED` is always allowed and encouraged: exposing a divergence
  is progress. What is forbidden is hiding one.
- The only exit from a monotonicity violation is a dedicated PR that changes nothing else, explains
  the regression, and is approved by the owner. Agents cannot self-approve it.
- A known divergence is a `FAIL` row with an issue, not an exclusion. D12-style accepted divergences
  require a DECISIONS.md entry.

### 3.5 What blocks further porting

Hard stops (controller starts no new translate-wave anywhere):
- T2 or T3 red on `main`.
- Any scoreboard row regressed.
- `regen --check` drift (a committed golden cannot be reproduced from Paper).
- The oracle is unbootable for more than one batch (UNVERIFIED streak). An unverifiable main is red.

Subsystem stops (no new waves in that subsystem; other subsystems continue):
- Debt over threshold (section 4).
- A milestone-terminal row for the subsystem is still `INACTIVE`/`UNVERIFIED` while units downstream
  of it are being ported. Concretely today: **no more worldgen feature fan-out (#600) before Stage A
  hash-diff or the `feature.place` sweep is live**, and **no M3 gameplay family wave (#404-#482) before
  the L4 arena harness and the generic codec op exist.**

## 4. Scaling: the verification-debt metric

### 4.1 Definition

`scripts/verify_debt.py` (new, offline, deterministic) reads the tree and `VERIFY.tsv`:

- Unit of account: non-test LOC of each `crates/*/src/**/*.rs` file (strip `#[cfg(test)]` modules and
  `tests.rs`/`*_tests.rs`; exclude `generated/` and files with a `@generated` header).
- Each file gets the best class among the ledger rows whose globs match it:
  - **V2** — a `PASS` row at layer L2-L6 (live differential), with a negative control;
  - **V1** — a `PASS` row at L1 (recorded golden with manifest provenance, reproducible by `regen`);
  - **V0** — no Java-sourced row.
- Guard against glob inflation: a row can credit at most `K * corpus_n` LOC (start with K = 50). A
  12-row JSONL cannot "verify" a 5,000-line module. The row's excess is reported as V0. This is the
  one tunable; set it once in a doc PR.

Outputs, per subsystem and total:
- `debt_loc = V0` and `debt_ratio = V0 / total`
- `thin_loc = V1` (verified only by frozen goldens)
- `debt_delta` since the last batch (did this batch add more unverified LOC than it retired?)
- reviewer-findings-per-unit trend, already called for in WORKFLOWS.md, printed alongside.

The script must also print the top 20 V0 files by LOC: that list *is* the verification backlog.

### 4.2 Thresholds

| Condition | Action |
|---|---|
| Subsystem `debt_ratio > 0.30` **and** `debt_loc > 10k` | No new port waves in that subsystem. Next workflow runs there are verification items. |
| Subsystem `debt_delta > 0` for 2 consecutive batches | Same: verification before the next wave. |
| Global `debt_ratio > 0.35` | Global pause on translate-waves; controller spends the next cycle on the top of the V0 list. |
| A new subsystem (no rows at all) | Its first wave must be preceded by its first op/arena (test-first), no exceptions. |
| Steady state target | Global `debt_ratio <= 0.15`, every subsystem with at least one V2 row. |

Where we are today, using the file-level grep as a stand-in for the ledger: 1,226 of 1,351 files
reference no fixture; at least 116k LOC (24%) are in buckets with none at all; applying the corpus cap
would push features, structures and most of `server/level` into V0 as well. The honest global
`debt_ratio` is well above 0.35. **By this policy the port is already paused in entity, items/gameplay,
worldgen features, brigadier and serialization.** That is the point: the next ~10 workflow runs should
be the list in section 5, not translate-waves in those subsystems. Subsystems under threshold
(protocol join path, NBT, registries, chunk storage) may continue.

### 4.3 Why this keeps up with throughput

Verification effort per ported unit must be sub-linear. It is, if the default mechanism is a generic
op: `codec.reencode` gains a new type with one line; `registry.eval` covers every new feature,
recipe, loot table or structure the moment its Rust handler exists; `packet.reencode` covers a new
packet with zero Java. Bespoke probes and bot scenarios are reserved for behavior no generic op can
reach. If the debt number rises anyway, the failure is architectural (a missing generic op), and the
response is to build that op, not to write 50 probes.

## 6. Changes to gate.sh, workflows and review prompts

### 6.1 `scripts/gate.sh`

1. **Per-step timing** and a one-line summary table at the end. We are tuning blind today.
2. **Explicit tiers**: `--tier scoped|merge|full|nightly` replacing the implicit "args = scoped, no
   args = everything". `full` stays the default so nothing weakens by accident.
3. **Path-triggered oracle rows** in `merge`: read `VERIFY.tsv`, intersect `rust_globs` with
   `git diff --name-only origin/main...HEAD`, run those rows plus the always-on live-op boot.
4. **One JVM, many checks.** `rivet-parity`, the reference self-test and all live ops share one oracle
   boot. The five codegen probes share one bundler JVM. Estimated saving: 6-8 launches.
5. **Capture mutations without re-booting.** `rivet-capture verify --mutate <kind>` x9 should mutate a
   single saved raw capture, not boot Paper nine times (verify whether it re-boots today; if it does,
   this alone removes ~9 boots). Same for the three `--expect-fail` oracle verifies: corrupt the
   baseline against one captured boot.
6. **Scenario server reuse.** `join`, `join both`, `move both` can share one Paper boot per world
   config (fresh bot identity per scenario); keep a fresh boot where world state is mutated.
7. **Build once.** The three test passes (`--workspace`, `rivet-registry --features blocks`,
   `rivet-protocol --features packets`) rebuild large crates. `rivet-server` already depends on
   both features, so check (not verified here) whether one invocation with
   `--features rivet-registry/blocks,rivet-protocol/packets` covers all three, or whether the features
   can simply become default and the flags be deleted (per the "no speculative configuration" rule).
   Either removes two rebuilds. Use `cargo nextest archive` if the scenario runner needs
   the same binaries.
8. **Promote silent states to ledger states.** `generated-full` "NOTICE — promotion is inactive" and
   `hash-diff` "NOTICE — did not run" become `INACTIVE` rows on the scoreboard. The gate stays
   mergeable, but the gap is printed in the final verdict every time.
9. **New steps**: `verify_debt.py --check` (thresholds, monotonicity) in `merge`; `regen --check` and
   fuzz in `nightly`; fixture-provenance check (every file under `fixtures/` is listed in a manifest
   with a SHA-256 and a producing op/probe) in `scoped`, since it is offline and fast.
10. **Lock scope.** The build lock exists to stop cargo builds competing. Paper boots and scenario runs
    do not need it once binaries are built: build under the lock, then release it for the JVM phase
    (ports are already isolated per tool). This lets T2 run while the next PR compiles. Watch RAM: cap
    concurrent JVMs at 2 on the 19 GB box.

### 6.2 Workflows (`.claude/workflows/*.js`)

- **`translate-wave.js`** — args gain `verification: [{row_id, mechanism, fixture_paths}]` per unit,
  filled by the controller from the ledger. The implementer prompt changes from "add round-trip or
  fixture-based tests" to: "these recorded goldens already exist for your unit; make them pass; do not
  edit them; if none exist, return `verification: none` and do not invent expected values". The report
  schema gains `rows_passing`, `rows_failing`, `uncovered_files`. A unit with `verification: none`
  converges as `ported-unverified`, which the controller counts as debt rather than `done`.
- **New `verify-surface.js`** (a thin specialization of `worktree-task`) — input: a ledger row to
  create (op or arena, Java classes, corpus recipe). Phases: write the Java handler and record goldens
  from Paper; prove twin-run determinism; add the tamper negative; add the Rust handler or leave it as
  the failing row; review. Reviewer lens: "does the Java side call the *production* Paper code path or
  a reimplementation of it? is the corpus registry-wide or hand-picked? can the Rust side pass
  vacuously?"
- **New `oracle-batch.js`** — the T2 runner: executes the full oracle tier, parses the ledger diff,
  opens/updates one `parity` issue per newly failing row with first divergence and artifact paths, and
  returns `{green, regressed_rows, new_fail_rows, debt}` for the controller's pause decision. This is
  the scripted form of the `verify-oracle` design in WORKFLOWS.md.
- **`release-prep.js`** — `checks` must include the scoped tier and the ledger check; the success
  record gains `ledger_rows_touched` and their status so the controller knows which oracle rows the
  merge gate will trigger.
- **`review-pr.js`** — add a mandatory section to the verdict schema, `verification`, with fields
  `expected_value_provenance_ok`, `fixtures_untouched`, `exclusions_untouched`,
  `uncovered_files[]`, `debt_registered`. `merge_ready` cannot be true if `uncovered_files` is
  non-empty and no debt is registered.
- **`check-burndown.js`** — add to the fixer rule: never change an expected value, fixture, or
  comparator to resolve a compile or test failure; a failing golden is a `blocked` finding.

### 6.3 Review prompt additions (all reviewer lenses)

Paste into every review prompt next to the drift checklist:

1. For each new assertion with a literal expected value: where did the value come from? Accept only
   (a) a recorded golden with a manifest, (b) a value the test derives from such a golden, or (c) a
   Rust-only invariant with no Paper counterpart. Flag everything else as `fabricated-expectation`.
2. Did the diff touch any file under `fixtures/`, any `*.jsonl`/`*.tsv` golden, any exclusion table,
   or any comparator/normalizer? In a port PR that is a blocking finding.
3. Can the test pass vacuously (empty corpus, `if let Some` around the assertion, a filter that drops
   every row, an early return when a file is missing)? Require closure counts.
4. Does a test compare Rivet output to Rivet output (round-trip only, snapshot of own output)? It earns
   no verification credit; say so in the finding and list the file as uncovered.
5. For Java probes/ops: does the handler call Paper's real code path, or does it re-derive the answer
   in the probe? A probe that reimplements logic is an oracle of itself.
6. Is any nondeterminism handled by widening the comparison (epsilon, sorting, dropping a field)
   instead of by seeding or by a recorded exclusion with a Paper twin-run justification?
